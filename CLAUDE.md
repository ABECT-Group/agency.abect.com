# CLAUDE.md — як працювати з проектом ABECT

Корпоративний сайт веб-агентства **ABECT**: https://agency.abect.com
Next.js 16 + Payload CMS 3.93 + MongoDB, мови UA/EN, деплой через Docker на VPS.

- **Репозиторій:** https://github.com/ABECT-Group/agency.abect.com
- **Документація:** [`docs/README.md`](docs/README.md)
- **Гілки, коміти, pull request:** [`docs/git-workflow.md`](docs/git-workflow.md) — обов'язково до прочитання
- **Мова спілкування й документації:** українська.

**Ролі.** Власник проекту рев'ює й мерджить pull request у `main` і деплоїть. Розробник працює у своїй гілці, комітить туди й відкриває PR. Claude працює **від імені розробника**: лише в робочій гілці, ніколи не в `main`.

---

## Порядок роботи Claude

### Крок 0. Гілка — СТРОГО, перед будь-якою іншою дією

Не читати код, не аналізувати, не змінювати файли, поки не визначена робоча гілка.

1. Подивитися стан:
   ```bash
   git status -sb
   git fetch --prune origin
   git branch -vv
   git branch -r
   ```
2. **Запитати розробника: «У якій гілці працюємо?»** Показати поточну гілку, список наявних гілок (локальних і `origin/*`, крім `main`) і запропонувати варіанти:
   - продовжити в одній з наявних гілок;
   - створити нову гілку від свіжого `main` (назва за правилами з [`docs/git-workflow.md`](docs/git-workflow.md#2-назви-гілок): `feature/…`, `fix/…`, `docs/…`, `chore/…`, латиницею в kebab-case).
   **Чекати на відповідь.** Не обирати гілку самостійно, навіть якщо вона здається очевидною.
3. Якщо є незакомічені зміни — **до** перемикання спитати, що з ними робити (закомітити в поточну гілку / `git stash` / залишити й не перемикатись). Нічого не відкидати (`checkout -- .`, `reset --hard`, `clean`) без прямого прохання.
4. Перемкнутися:
   ```bash
   # наявна гілка
   git switch <гілка> && git pull --ff-only
   # нова гілка
   git switch main && git pull --ff-only && git switch -c <нова-гілка>
   ```
   Якщо `pull --ff-only` не проходить (гілка розійшлася з origin) — зупинитися й спитати розробника.
5. Якщо розробник відповів «`main`» — пояснити, що в `main` зміни потрапляють лише через pull request, і запропонувати створити гілку. Працювати в `main` не можна.
6. Підтвердити одним рядком: «Працюємо в гілці `<гілка>`, відставання від `origin/main`: N комітів».

Перевіряти гілку (`git branch --show-current`) **перед кожним комітом**. Якщо раптом опинилися в `main` — зупинитися й повідомити.

### Крок 1. Аналіз

Мовчки зібрати контекст:

1. **Стан репозиторію**
   ```bash
   git log --oneline -15 --date=short --format='%h %ad %s'
   git log --oneline main..HEAD          # що вже є в робочій гілці
   git log --oneline HEAD..origin/main   # чого з main бракує гілці
   ```
   Незакомічені зміни, відставання від `origin/main`, відкриті PR (`gh pr list`, якщо `gh` доступний) — згадати у звіті.
2. **Останні зміни:** [`docs/changelogs/changelog.md`](docs/changelogs/changelog.md), потім 2–3 найсвіжіші файли днів (що робили, що лишилось незавершеним, «не робилось» / «наступні кроки»).
3. **Поточні проблеми:** [`docs/issues/current.md`](docs/issues/current.md). Насамперед 🔴 і 🟠.
4. **Контекст задачі:** якщо розробник уже назвав задачу, прочитати потрібні розділи [`docs/architecture.md`](docs/architecture.md), [`docs/patterns.md`](docs/patterns.md), [`docs/api.md`](docs/api.md) і файли коду, яких вона стосується.

### Крок 2. Короткий звіт розробнику

5–10 рядків:
- робоча гілка, незакомічені зміни, відставання від `origin/main`, відкриті PR;
- що робилось останнім (з ченджлогу);
- відкриті критичні та високі проблеми (ID + одна фраза);
- якщо задача названа: як я її розумію і що вона зачіпає.

### Крок 3. Питання розробнику — що робити

Запитати, а не починати самому:
- якщо задачі немає, запропонувати 2–4 варіанти з пріоритетом (починаючи з 🔴 з `issues/current.md`);
- якщо задача є, уточнити лише те, що реально впливає на рішення (обсяг, підхід, чи можна чіпати суміжне);
- для ризикових дій (security, `access`, залежності, Docker, видалення файлів) отримати явне «так».

### Крок 4. Робота

- Правила, заборони і код-стайл — [`docs/rules.md`](docs/rules.md). Патерни — [`docs/patterns.md`](docs/patterns.md).
- Мінімальна зміна під задачу. Побачене по дорозі не виправляти, а записати в `issues/current.md`.
- Перевірити: `npm run typecheck`, `npm run lint`, за потреби `npm run build` (див. [`docs/rules.md`](docs/rules.md#7-перевірки-перед-завершенням-задачі)).

### Крок 5. Документування (обов'язково, інакше задача не завершена)

1. **`docs/changelogs/YYYY-MM-DD.md`** (сьогоднішня дата). Якщо файлу немає, створити. Новий запис додається **зверху** файлу:
   ```markdown
   ## Запит N — <коротка назва>

   **Гілка:** `feature/…` · **PR:** #… (якщо вже є)
   **Запит розробника:** <що просили>

   ### Зроблено
   - <що і чому> (`шлях/до/файлу`)

   ### Перевірено
   - typecheck / lint / build / вручну — результат

   ### Не робилось / наступні кроки
   - …
   ```
2. **`docs/changelogs/changelog.md`** — індекс: для кожного дня заголовок-посилання і **короткий опис** (1–3 речення простою мовою: що змінилось і навіщо, без переліку файлів). Деталі — лише у файлі дня.
   - Якщо дня ще немає — додати блок **першим** (одразу після `---` під шапкою):
     ```markdown
     ### [YYYY-MM-DD](YYYY-MM-DD.md)
     Короткий опис змін за день.
     ```
   - Якщо день уже є — доповнити його опис новою задачею (опис має охоплювати всі запити дня).
3. **`docs/issues/current.md`**: нові проблеми додати з наступним `ISS-XXX` і внести в зведену таблицю. Виправлені **перенести** в `docs/issues/resolved.md` (зверху, з датою і посиланням на ченджлог).
4. Якщо змінилися API, архітектура, патерни чи деплой, оновити відповідний файл у `docs/`.
5. Фінальна відповідь розробнику: що зроблено, що перевірено, що лишилось, чи готово до коміту / PR.

### Крок 6. Коміт, пуш, pull request (лише на прохання розробника)

Детально — [`docs/git-workflow.md`](docs/git-workflow.md). Коротко:

```bash
git branch --show-current                 # НЕ main
git add <конкретні файли>                 # не додавати .env, media/, .next/
git commit -m "feat: коротко що зроблено"
git push -u origin <гілка>
gh pr create --base main --head <гілка> --title "…" --body "…"   # опис за шаблоном PR
```

- Один PR = одна задача. Якщо PR уже відкритий для цієї гілки — просто пушити нові коміти в ту саму гілку.
- Перед PR: гілка оновлена з `main` (`git fetch && git merge origin/main`), typecheck / lint / build проходять, ченджлог оновлено.
- Якщо `gh` недоступний — дати розробнику посилання `https://github.com/ABECT-Group/agency.abect.com/compare/main...<гілка>`.
- **Мерджить лише власник.** Claude ніколи не мерджить PR і не пушить у `main`.

## Жорсткі обмеження

- ❌ Жодних комітів, пушів чи мерджів у `main`. `main` змінюється тільки через PR, який мерджить власник.
- ❌ Не комітити, не пушити, не відкривати PR без прямого прохання розробника. Повідомлення комітів — змістовні (`feat: …`, `fix: …`, не `update`).
- ❌ Не робити `git push --force`, `reset --hard`, `rebase` вже запушених гілок, не видаляти чужі гілки — без прямого прохання.
- ❌ Не деплоїти й не виконувати нічого на VPS (деплой — справа власника).
- ❌ Не читати й не виводити вміст `.env`, `.env.prod` чи будь-яких секретів.
- ❌ Не писати в продакшн-БД і не слати POST або мутації на живий сайт. Для перевірок — лише GET без персональних даних.
- ❌ Не правити згенеровані файли (`src/payload-types.ts`, `src/app/(payload)/**`). Замість цього запускати `npm run generate:types` / `generate:importmap`.

## Швидка шпаргалка

```bash
npm run dev                 # http://localhost:3000, адмінка /admin
npm run build               # БД не потрібна: достатньо заглушок PAYLOAD_SECRET / DATABASE_URI
npm run generate:types      # після зміни колекцій
npm run typecheck && npm run lint
```

| Що | Де |
|---|---|
| Сторінки | `src/app/(frontend)/[locale]/**/page.tsx` |
| Секції сторінок | `src/client/modules/<page>/` |
| Спільні компоненти | `src/client/components/` |
| Запити до CMS | `src/client/lib/*.ts` через `payloadFetch` (тег `'all'`) |
| Колекції / global | `src/collections/`, `src/globals/`, права — `src/access/` |
| Заявки → Telegram | `src/app/api/leads/route.ts`, `src/utils/telegram.ts` |
| Переклади | `messages/ua.json` + `messages/en.json` (завжди обидва) |
| Security-заголовки, CSP | `next.config.mjs` |
| Локалі / rewrite | `src/proxy.ts` (Next 16), `src/client/i18n/` |
| Деплой | `docs/deployment.md`; скрипти й MongoDB — `../scripts/`, `../mongodb/` (поза git, лише у власника) |

Нюанс локалей: URL використовує `ua`/`en`, Payload — `uk`/`en` (див. `docs/architecture.md`).
