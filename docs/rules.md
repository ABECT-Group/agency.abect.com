# Правила роботи та best practices

Ці правила обов'язкові і для людей, і для Claude. Порядок роботи Claude описаний у [`../CLAUDE.md`](../CLAUDE.md).

## 1. Загальні принципи

1. **Спочатку зрозуміти, потім змінювати.** Перед правкою прочитати файл цілком і знайти схожі місця (`grep`). Якщо вже є патерн, використати його ([patterns.md](patterns.md)).
2. **Мінімальна зміна під задачу.** Не рефакторити «заодно» і не переформатовувати файли, яких задача не стосується. Побачене по дорозі записати в `docs/issues/current.md`.
3. **Не вигадувати.** Назви полів беруться з `src/payload-types.ts` і колекцій, ключі перекладів — з `messages/*.json`, env-змінні — з `.env.example`. Нічого не існує, поки це не перевірено.
4. **Безпека понад зручність.** Будь-яка зміна `access` у колекціях, API-роутів, заголовків чи env розглядається як security-зміна і окремо описується в ченджлозі.
5. **Документація — частина задачі.** Зміна без запису в ченджлог не вважається завершеною (див. розділ 8).

## 2. Заборони (без явного дозволу розробника)

- ❌ Будь-які коміти, пуші й мерджі в `main` — лише через PR, який мерджить власник ([git-workflow.md](git-workflow.md)).
- ❌ Коміт, пуш, відкриття PR у робочій гілці — лише на прохання розробника.
- ❌ `git reset --hard`, `push --force`, rebase запушених гілок, видалення чужих гілок.
- ❌ Деплой, запуск `../scripts/*.sh`, будь-які дії на VPS.
- ❌ Читати або виводити вміст `.env`, `.env.prod` чи будь-яких секретів. Можна дивитися лише імена ключів.
- ❌ Записувати в продакшн-БД (seed, POST/PATCH в API продакшну). Для перевірок у роботі — локальна тимчасова БД.
- ❌ Ручні правки згенерованих файлів: `src/payload-types.ts`, `src/app/(payload)/**` (крім `custom.scss`), `importMap.js`.
- ❌ Оновлювати мажорні версії залежностей і змінювати `package-lock.json` без узгодження.
- ❌ Видаляти файли поза завданням.
- ❌ Масове переформатування коду Prettier-ом (див. 3.2).

## 3. Код-стайл

### 3.1 TypeScript
- `strict`, **без `any`** (ESLint: `no-explicit-any: error`). Якщо тип невідомий, використати `unknown` і звузити.
- Типи даних CMS брати з `@/payload-types` (`Service`, `Post`, `Portfolio`…). Власні дублікати не писати.
- Імпорти через аліаси: `@/…` (src), `@payload-config`.
- `as unknown as X` — лише на межі з Payload API і з коментарем, чому так.

### 3.2 Форматування
- `.prettierrc.json` вимагає: одинарні лапки, без `;`, ширина 100. **Але фактичний код неоднорідний** (у багатьох файлах є `;` і таби). Правило таке: **дотримуватися стилю файлу, який редагуєш.** Масове вирівнювання — окрема задача.
- Коментарі пишуться українською або англійською. Російською не можна.

### 3.3 React / Next.js
- Серверні компоненти за замовчуванням. `'use client'` додавати лише там, де потрібні стан, ефекти чи браузерні API.
- `page.tsx` відповідає лише за отримання даних, `generateMetadata`, JSON-LD і рендер модуля. Верстка живе в `src/client/modules/<page>/`.
- Компонент складається з папки з `Component.tsx` і `Component.scss` поруч.
- Не звертатися до `window` чи `localStorage` під час рендеру. Для стану з браузерних сховищ — `useSyncExternalStore` (приклад: `useCookieConsent`), не `useEffect` + `setState`; доступ — через `try/catch`.
- Зображення: `next/image` з `alt` (обов'язково, з i18n).
- Посилання й навігація: `Link` / `useRouter` з `@/client/i18n/navigation` (додають локаль), а не з `next/link` і не `window.location`.

### 3.4 Стилі
- SCSS-файл поруч із компонентом, класи за BEM-подібною схемою від імені компонента (`.service-hero__title`).
- Глобальні змінні та міксини задаються в `globals.scss`. Нові кольори або брейкпоінти додавати туди, а не хардкодити.
- Файли стилів глобальні (не CSS Modules): `:global(...)` у них невалідний і мовчки відкидається.
- Поважати `prefers-reduced-motion` для анімацій.

### 3.5 i18n
- **Жодного хардкоду тексту в UI.** Кожен рядок додається в **обидва** файли: `messages/ua.json` та `messages/en.json`, з однаковим ключем.
- Контент із CMS запитується з `locale` (див. [architecture.md](architecture.md#локалі--важливий-нюанс)).
- Нова сторінка потребує обох мов, `alternates.languages` (ua, en, x-default → en) і запису в `sitemap.ts`.

## 4. Payload CMS

- Нова колекція або global: файл у `src/collections` (`src/globals`) → реєстрація в `payload.config.ts` → `npm run generate:types` → `npm run generate:importmap` (якщо є кастомні компоненти адмінки).
- **Обов'язково** додати хуки `afterChange` і `afterDelete` → `revalidateAll` (`src/hooks/revalidate.ts`), інакше сайт не побачить змін.
- **Обов'язково** явно прописати `access` через хелпери `src/access/index.ts`. Публічний `read` — лише для контенту сайту (зі статусом — `publishedOrAuthenticated`). Заявки, користувачі та будь-які персональні дані — тільки для залогінених. Матриця прав — [api.md](api.md#матриця-доступів).
- GraphQL вимкнено. Не вмикати без потреби; якщо ввімкнути — перевірити, що access-правила покривають усі колекції.
- Текстові поля для сайту позначати `localized: true`.
- Числа (ціни) — з `min: 0`, URL — з валідацією.
- Нагадування: Payload Local API (`payload.find/create`) **за замовчуванням ігнорує access** (`overrideAccess: true`). Це зручно на сервері, але небезпечно, якщо дані йдуть від користувача без валідації.

## 5. API та безпека

- Кожен вхідний payload валідується на сервері: тип, довжина, формат. Клієнтській валідації не довіряти.
- Публічні POST-ендпоінти потребують rate limit, перевірки Origin і обмеження розміру тіла.
- IP клієнта брати з `X-Real-IP` (його ставить nginx), а не з першого значення `X-Forwarded-For`, яке клієнт може підробити.
- Секрети існують лише як env-змінні. Змінні з `NEXT_PUBLIC_*` потрапляють у браузер і **вшиваються під час білда** (у Docker — через build args, див. [deployment.md](deployment.md)).
- Зовнішні виклики (Telegram) робити з таймаутом (`AbortController`) і не блокувати ними відповідь користувачу.

## 6. SEO (кожна публічна сторінка)

- `generateMetadata`: `title`, `description`, `alternates.canonical`, `alternates.languages`, `openGraph` (`locale: uk_UA / en_US`, `images`), `twitter`.
- JSON-LD: `BreadcrumbList` + тип сторінки (`Service`, `Article`, `CreativeWork`…).
- Один `<h1>` на сторінку.
- Службові сторінки (`/thx`) мають `robots: { index: false }`.
- Абсолютний домен — лише через `SITE_URL` (`src/client/config/site.ts`).
- OG-зображення: `public/seo/<page>-og.jpg` і `en-<page>-og.jpg`, 1200×630.

## 7. Перевірки перед завершенням задачі

```bash
npm run typecheck         # tsc --noEmit
npm run lint              # ESLint (0 помилок і 0 попереджень)
npm run build             # якщо зачеплені сторінки, конфіги, залежності
npm audit --omit=dev      # якщо змінювались залежності
```

Для `build` достатньо заглушок: `PAYLOAD_SECRET=x DATABASE_URI=mongodb://placeholder@127.0.0.1:27017/x npm run build` (БД на білді не використовується).

Автотестів немає (шаблонні видалено 2026-11-09). Зміни роутингу, proxy, кешу чи API перевіряти в роботі: `node .next/standalone/server.js` з локальною тимчасовою MongoDB (див. ченджлог 2026-11-09).

## 8. Definition of Done

Задача завершена, лише якщо виконано все:

- [ ] Код працює, `tsc` і `lint` без нових помилок.
- [ ] Переклади додані в обидві мови.
- [ ] Оновлено `docs/changelogs/YYYY-MM-DD.md` (новий запис **зверху** файлу) і `docs/changelogs/changelog.md` (посилання на день **зверху** списку, якщо дня ще немає).
- [ ] Знайдені й не виправлені проблеми додані в `docs/issues/current.md`. Виправлені перенесені в `docs/issues/resolved.md` з датою.
- [ ] Якщо змінилися API, архітектура, деплой чи патерни, оновлено відповідний документ у `docs/`.
- [ ] Розробнику дано короткий звіт: що зроблено, що перевірено, що лишилося.
